## Bug 1 — status corrections logged as new hypothesis_ids never took effect

`src/research_ledger.py`'s `get_latest()`/`get_current_state()` resolve a
hypothesis's current status by scanning for rows with a MATCHING
`hypothesis_id`. Several 2026-09-09 "STATUS_CORRECTION" audit passes
logged their correction as a brand-new hypothesis_id with a `corrects`
parameter pointing at the real one, instead of calling `update_status()`
on the original id -- so the correction was written to disk but never
actually changed what `get_current_state()` reports. A full audit this
cycle of all 10 `corrects`-style entries in the ledger found 4 that were
still un-applied: hyp-000023, hyp-000025, hyp-000027 (correction entries
hyp-000097/098/099, 2026-09-09) and hyp-000051 (correction entry
hyp-000125, 2026-09-09 TRIAGE SWEEP). The other 6 had since been fixed
properly. (2 more involving H118's own family, hyp-000121/hyp-000126,
are handled correctly by pipeline_sweep.py's separate FAMILY_HEADS logic
and are out of automated scope regardless -- flagged, not touched.)

Fixed by calling `update_status(<id>, "REJECTED", notes=...)` directly on
each of the 4, carrying forward the exact disposition and reasoning the
2026-09-09 correction already gave (all four: required prospective test
already ran and failed/was inconclusive, or -- hyp-000051 -- n=9 is the
textbook example motivating this project's own MIN_N_FOR_PROMISING=40
rule). No new data touched, no new hypothesis ID spent, H118/EXP047
untouched.

## Bug 2 — stale bookkeeping rows fabricated phantom OPEN/GATED candidates

`pipeline_sweep.py`'s re-expression handling (MULTIPLICITY_REEXPRESSION /
PROGRESSION_POINTER rows) looks for a live row belonging to the same
parent idea; when none exists it assumed the parent must be a genuinely
orphaned candidate and fabricated a synthetic OPEN/GATED row for it --
never checking whether the parent had, in fact, already been closed via
a proper `update_status()` call on its own id. Once Bug 1's fix (and an
earlier, correctly-applied 2026-09-10 closure) took hyp-000048 and
hyp-000056 out of the `live` set, their bookkeeping children (hyp-000131,
hyp-000132/129) triggered exactly this path every cycle, re-appearing as
"OPEN hyp-000048 ... OWED: Director Re-Evaluation" and "GATED hyp-000056
... OWED: Director Re-Evaluation" -- both already REJECTED for a session
or more. Fixed: the fallback now checks the parent's real current status
and marks the row `hidden` (not rendered, but still counted for the
completeness test) when the parent is already closed. Regression test
added: `test_closed_parent_bookkeeping_row_is_hidden_not_phantom_owed_work`.
